The hard part of AI code modernization isn’t the code

AI agents can now carry a large modernization in weeks instead of years — but the organizational work on either side barely changes. This is the prep that decides whether the run succeeds: a target everyone agrees on, machine-checkable evidence, and a review policy that scales.

The idea in five lines

  • Agents got fast; orgs didn’t — modernization can finish in weeks, but change management and approvals in regulated shops still gate the work.
  • Pick one target — Uplift (same stack, new version), Transform (new stack, same behavior), or Reimagine (greenfield rebuild) — before anyone writes code.
  • Write a certificate — the machine-checkable conditions every change must pass: tests, coverage thresholds, performance, security scans, old-vs-new parity.
  • Set a promotion policy — tier changes by risk so reviewers aren’t the bottleneck, and make the directive come from leadership, not individual approvers.
  • Pilot, then extrapolate — run a small partition first, measure token usage and the full end-to-end process, then scale.
So what for you

If you’re weighing a modernization, start by writing the certificate with the people who will approve changes into production — the agent’s speed is wasted without an agreed, automatic definition of “correct” and a tiered way to say yes at scale.

Step one

Agree on the target before writing code

Modernization means different things to different people, and leaving that unresolved is the classic failure. The guidance names three end-states. Decide which one you’re doing, with consensus, up front — and use Claude’s discovery to map current systems and extract business logic, surfacing the unknown dependencies and edge cases that derail runs later.

Uplift

Same stack, new version

Version bumps within the existing technology stack — the smallest-scope option.

Transform

New stack, same behavior

A cross-stack rewrite that preserves what the system does today.

Reimagine

Greenfield rebuild

A fresh build that also changes functionality — the broadest, riskiest scope.

Both positions are reasonable, but if the question is left unresolved it resurfaces later as an argument over whether a given change is “correct.”

Why it works

A certificate, and a policy for saying yes

Agents produce changes faster than humans can review them one by one. Two artifacts keep that from becoming a bottleneck. The certificate is the set of conditions every change must meet, checkable without a human in the loop. The promotion policy tiers changes by risk and confidence, so low-risk changes flow and scrutiny concentrates where it matters.

In regulated environments the real blocker is accountability: individual approvers hesitate because they personally carry the risk of a bad change. The fix is organizational — the directive to adopt tiered promotion should come from leadership, distributing responsibility rather than isolating it on one reviewer’s desk.

Certificate

What it checks

Original test-suite passage, new coverage thresholds, performance benchmarks, security-scan results, and parity between old and new versions — written with the people who promote changes to production.

Prerequisites

What to have ready

Dedicated remote hosts with codebase access, test capacity for the certificate, CI/CD updates, security and compliance sign-off for source access, and least-privilege controls.

Plan the spend

What drives cost — and how to estimate it

Main cost drivers are the ratio of code read to code modified, how complex the certificate is to verify, the volume of test writing and repair, and reconciliation work when development continues in parallel. The recommended move is empirical: run the modernization on a small part of the codebase, measure token usage, and extrapolate for the rest of the run. Risk reduction is often the biggest benefit — weigh the risk of not modernizing when deciding whether to go.

Before you start

Write the certificate with your reviewers, get the promotion-policy directive from leadership, and pilot on a small partition to measure token usage before you scale. Treat the workflow, certificate, and policy as reusable assets for the next modernization.
