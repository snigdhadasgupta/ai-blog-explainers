Governing Third-Party AI Agents

AI that advises became AI that acts — retrieving records, moving money, routing documents, often with no human in the loop. Box’s argument: a clean vendor review tells you nothing about what any single agent can actually do inside your systems.

The idea in five lines

  • Vendor vetting is not governance — two agents from the same trusted vendor can carry very different risk, so you govern each one by its access, autonomy, authority, and potential impact.
  • Two levers, not one: least privilege limits the data and tools an agent can reach; least agency limits the actions it can take on its own. An agent that recommends a refund doesn’t need to issue one.
  • Observability is not enough — a log shows a threshold was crossed after the fact; governance stops or reroutes the action before it happens.
  • Enforce at execution time: inventory, classify, limit, enforce boundaries as the agent acts, then monitor — a five-step cycle, because agents move at software speed.
  • Watch the delegation chain: authority should not auto-pass from an internal agent to a third-party one; each hop gets only the context and permissions its step needs.
So what for you

Before you let a vendor’s agent into a real workflow, write down what it can see and what it can do — two separate questions — and put a human approval step on anything consequential (money, records, external sends). “We approved the vendor” is not an answer to “who authorized this action?”

Why it matters

The risk moved from “what can it see” to “what can it do”

Traditional vendor risk asks whether a provider is secure and compliant. Agents force a sharper question: what can this agent actually do? An agent that summarizes public information is nothing like one that retrieves customer records or changes a financial account — even if they come from the same vendor and passed the same review.

Speed is what makes mistakes expensive. One customer-service agent giving a single traveler the wrong flight time is containable. An autonomous agent repeating that error across thousands of interactions is a different kind of problem — and only a control that operates while the agent acts can catch it before it spreads.

“Agents will find everything.” — Aaron Levie, CEO of Box. Something you shared five years ago and forgot, the agent will go and find.

The two levers

Least privilege and least agency are not the same control

Least privilege

Limits what it can reach

Grant only the data, systems, and tools the task requires. A finance agent can reconcile transactions with read access to the ledgers it needs — and nothing else.

Least agency

Limits what it can decide

Grant only the decision-making and execution authority the task requires. The same finance agent flags discrepancies, but changing a financial record still needs a human signature.

Teams that collapse these into one “permissions” setting tend to over-grant: giving an agent the ability to act because they already gave it the ability to see. Keeping them separate is what makes safe delegation possible.

A distinction teams miss

Observability tells you what happened. Governance decides what’s allowed.

Observability

Reconstructs the past

Which tools the agent used, how it performed, where an error occurred. For a refund above a threshold, the log shows — afterward — that the limit was exceeded.

Governance

Intervenes in the present

Defines permitted behavior, assigns accountability, and provides a way to stop or reroute. The same refund is halted or sent for approval before it is issued.

You need both. But a dashboard that only records behavior is not a control — and many “agent governance” programs are really just logging.

The playbook

A governance cycle that runs at software speed

Figure 1 · Five steps, enforced while the agent acts — not quarterly
1

Inventory

Record ownership, operator, purpose, environment, and third-party dependencies.

2

Classify

Evaluate autonomy, access, authority, and potential consequences per agent.

3

Limit

Give each agent only the permissions and decision rights its work requires.

4

Enforce

Pause, redirect, approve, or halt actions that exceed defined limits.

5

Monitor

Preserve evidence, investigate, and revisit controls when anything changes.

↻ Reassess whenever an agent’s model, tools, permissions, provider, or business purpose changes.

Before an agent touches a consequential process, the inventory should answer five questions: who operates it, what purpose it serves and where it runs, which systems and data it can reach, whether it can recommend / approve / execute on its own, and whether it is part of a multi-agent or multi-tool deployment.

The hardest part

Delegation chains break single-component reviews

A single task can pass from a person to an internal agent, then to a third-party agent, an external tool, and finally an enterprise system. Review each component on its own and you still can’t say who authorized the end action. Trust and authority should not travel the chain automatically — a third-party agent handling one delegated step should receive only the context and permissions that step needs, with identity and accountability tracked across environments run by different providers.

Box Hubs

Permission-inherited content

An agent acting on someone’s behalf can’t reach anything that person couldn’t already reach — least privilege by default.

Box MCP Server

No standing grant

When an external agent pulls from Box, it inherits the requesting user’s existing permissions instead of a permanent grant of its own.

Relay + Sign

Approval before action

Box Relay and Box Automate insert a sign-off step so a recommendation becomes an executed action only after a human approves — and Box Sign captures the signature.

Box’s own caveat is worth repeating: content controls and workflows are part of a governance design — not a universal runtime control plane for every third-party agent. Content governance and agent-runtime governance are both needed; neither replaces the other.

Where to start this quarter

Build an agent inventory with an owner and purpose for each one, then classify by impact. Separate “can see” from “can do,” put enforceable approval steps on consequential actions, and make sure authority doesn’t silently pass down delegation chains. Treat it as a repeating cycle, not a one-time policy doc.
