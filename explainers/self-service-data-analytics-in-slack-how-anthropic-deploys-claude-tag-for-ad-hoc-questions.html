Self-Service Analytics in Slack

Anthropic put its governed data model behind a Slack agent (Claude Tag) so anyone can ask data questions and get answers backed by the same definitions analysts use. Five hard-won lessons on distribution, permissions, freshness, and observability.

The idea in five lines

  • Accuracy and deployment differ — getting an agent right is one motion; getting it usable by non-analysts in Slack is another, with its own rules for distribution and trust.
  • Treat skills as served content — Claude Tag re-reads the data repo’s skills/ directory every conversation, so a renamed column or fixed metric lands fast instead of giving last Tuesday’s confident wrong answer.
  • Teach the agent to work — knowledge skills tell it where data lives; runbook skills (forecasting, cohorts, funnels, charting) tell it how an analyst would actually use it.
  • Permission the service account — the bot queries as a service account, so everyone who can mention it has its access — scope it to governed data, deny PII clearance, and treat channel membership as a grant.
  • Instrument every answer — log which skills loaded, thumbs up/down and corrections, and data-quality warnings; the share of queries routed through the governed layer was the most actionable metric.
So what for you

If you’re rolling out an AI agent over company data, decide what its service account can read before you write any agent code — widening access later is easy, clawing it back is not — and log every answer from day one so you can tell whether people actually trust it.

Why Slack changes the problem

Getting accurate and getting deployed are different jobs

In a prior post, Anthropic’s data team described reaching ~95% accuracy on analytics questions in Claude Code through a governed semantic layer, skill files, and an eval suite. Putting that same foundation where the rest of the company works — Slack, via Claude Tag — turned out to be a different motion entirely.

Non-analysts ask open-ended, ambiguous questions and can’t sniff-test a lone number in Slack the way they could reading a dashboard. That makes a confidently wrong answer especially damaging.

The single most important decision was to treat skill files as served content, refreshed continuously — if Claude reads last Tuesday’s copy, it gives last Tuesday’s wrong answer with full confidence.
The five lessons

Deploying a data agent where non-analysts live

Figure 1 · Five deployment learnings
Freshness

Re-read skills every turn

The runtime mounts the data repo’s skills/ directory and re-reads it on every conversation, so metric and schema changes land within an SLA.

Analyst skills

Beyond knowing what to query

Alongside the knowledge skill, mount runbooks for forecasting, cohort/retention, funnels, charting, and analytical writing — how an analyst works, not just where data lives.

Business context

Wire in the knowledge index

“Why did sign-ups drop Tuesday?” lives in incidents and Slack, not the warehouse. Connecting an internal knowledge index is the highest-leverage add after the data itself.

Permissions

Scope the service account

Everyone who can mention the bot has its access. Scope it deliberately — see below.

Telemetry

Instrument every answer

Log skills loaded and versions, reactions and corrections, and data-quality warnings, surfaced in the answer footer.

Permission the service account

A shared read replica of your governed warehouse

Claude Tag queries the warehouse as a service account, not as the human asking. That’s the right design — but it means there’s no per-user row-level security: what the service account can read, anyone in the channel can ask about. Anthropic scopes it five ways.

Scope

Governed data only

The account reads the semantic layer’s output tables and curated marts — not raw streams, staging, or sandboxes. Out-of-bounds questions get a refusal, not a guess.

Classify

Deny PII clearance

Column-level lineage flags likely PII for human review; the account holds no PII clearance, so sensitive columns are simply unreadable even in a queryable table.

Document

Put the connection in the skill

The skill spells out how the agent connects and authenticates, so it can fail cleanly and explain its own constraints instead of silently querying the wrong project.

Govern access

Membership is a grant

Adding Claude to a channel grants those members read access to what it can query; the data team owns the channel list. Every query is labeled for cost attribution and audit.

What it unlocks

Threads become the new meeting

The most effective Claude Tag threads have several people in them, contributing context while Claude does the legwork — and because threads are open, readers pick up what broke and how it was fixed without anyone writing a summary. Keep the agent in shared channels and keep work in threads, not DMs, so the thread is a reviewable record.

Recurring work moves to loops: proactive pre-standup readouts, multiple-times-a-day experiment monitoring, pipeline observability that drafts a fix and pings on-call, and triage of a data-questions channel. In one channel over a month, Claude Tag answered more than 75% of questions posted, usually within a minute, often without being called.

Getting started, in order

Permissions first — decide what the service account can read before writing agent code. Then distribution and verified freshness, telemetry from day one, the knowledge index once the data path is stable, and analyst skills last, informed by the questions people actually ask.
