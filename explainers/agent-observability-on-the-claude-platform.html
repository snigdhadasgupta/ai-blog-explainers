Agent observability on the Claude Platform

Claude Managed Agents, the Messages API, and the Claude SDKs can now send OpenTelemetry traces to any OTel tool. You can follow every step an agent takes — and that visibility is what lets you safely widen its access.

The idea in five lines

  • Agents now emit OpenTelemetry — traces from Managed Agents, the Messages API, and the SDKs flow to any OTel-compatible tool.
  • Trace, then trust — watch an agent’s model calls, tool use, and MCP calls first, and widen its access only as it proves reliable.
  • Standard conventions, your tools — traces follow OpenTelemetry’s GenAI semantic conventions, so Claude data sits beside the rest of your stack.
  • One setup step — add a destination in the Claude Console (SDKs export automatically); each turn arrives with latency, tokens, and IDs.
  • Three jobs it unlocks — debug agents next to your logs, turn production traces into evals, and track token usage by team across the org.
So what for you

If you’re moving agents toward production, you can’t govern what you can’t see. Point Claude’s traces at the observability tool your platform team already runs — Datadog, Grafana, Splunk, Langfuse and others are supported — so agent behavior shows up next to the rest of your stack, then use that record to widen an agent’s permissions deliberately instead of all at once.

Why it matters

Visibility is the precondition for access

Giving an agent more access is a trust decision, and trust starts with being able to see what it already does — its model calls, the tools it invokes, and the MCP servers it reaches. Review those traces, confirm the agent behaves, then widen access. Observability turns “we think it’s fine” into evidence.

If you already send Claude Code or Cowork traces to an observability tool, agents built on the Claude Platform can land in the same place — no separate pane of glass for the agent layer.

Trusting an agent with more access starts with being able to see what it already does.

Works with the tools you run

Three jobs, one standard format

Traces follow the OpenTelemetry GenAI semantic conventions, so data from Claude and other providers works in the same tools and dashboards. The article groups the named integrations by what you’d use them for:

Debug

Next to your stack

Grafana Cloud, Honeycomb, Sentry, Splunk — agent traces sit beside logs and metrics, so you can see which service a slow or failed step came from.

Improve

Production data → evals

Arize, Braintrust, Datadog, Langfuse, LangSmith, New Relic, PostHog — turn real traces into evals, catch quality issues, and measure whether a change actually helped.

Govern

Usage across the org

Send traces to Databricks Unity Gateway so platform and security teams can see token usage by team and flag unusual activity.

Any other OpenTelemetry tool that accepts a standard OTLP endpoint works too — the point is you don’t adopt a new monitoring stack to watch your agents.

Customer signal

Ramp’s improvement loop

Ramp built Reflect, an agentic system that scores its Langfuse traces, finds recurring failures, and proposes fixes. Its own reported result: “On some agents, we’ve already cut token usage by 10–20% and made sessions 30% faster.” — David Traina, Ramp. (A single customer’s figures, not an Anthropic benchmark.)
