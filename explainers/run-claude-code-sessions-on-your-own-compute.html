Self-Hosted Environments for Claude Code

Now in public beta, self-hosted environments let Claude Code sessions run on your own infrastructure — inside your network, next to your internal services and security controls — so repository checkouts, build artifacts, and secrets never leave infrastructure you control.

The idea in five lines

  • Run agents on your own compute — a public beta that executes Claude Code sessions inside your network rather than on Anthropic-hosted infrastructure.
  • Built for three needs — reaching internal services without public exposure, pre-installing your toolchain, and keeping source code and build artifacts on infrastructure you control.
  • Code stays, conversation travels — checkouts, artifacts, and secrets stay local; prompts, responses, and tool results (which can include code Claude reads) still go to Anthropic for inference.
  • Runners do the work — long-lived processes pick up sessions in fixed or on-demand modes, each session isolated in its own checkout.
  • Not the default choice — Anthropic still recommends its hosted option for most enterprises; self-hosting is for network, tooling, or compliance requirements and needs a team to own it.
So what for you

If your blocker to adopting coding agents is “our code and build systems can’t leave our network,” this removes it — but budget for a platform team to build and maintain the runner image and orchestration. If you don’t have that constraint, the managed hosted option is simpler and the recommended path.

Why it exists

When agent execution has to stay inside your walls

Some teams can’t send agent execution to a vendor’s cloud — their network, tooling, or compliance rules require keeping it on infrastructure they operate. Self-hosted environments answer that: a session started from web, mobile, desktop, or a routine runs next to your internal services, toolchains, and security controls. Anthropic is explicit that this isn’t the path for everyone — most enterprises should take the hosted offering for operational simplicity — but for the teams that need it, it closes a real gap.

Network

Reach internal systems

Sessions run inside your network and can reach internal services, databases, and registries without exposing them to the public internet.

Customizability

Pre-loaded toolchain

Pre-install compilers, SDKs, and internal CLIs so every session starts ready to build in your environment.

Compliance

Artifacts stay put

Source code and build artifacts remain on infrastructure you control, satisfying data-residency and compliance requirements.

The honest boundary

What stays local — and what still leaves

Figure 1 · Where each piece lives

Stays on your infrastructure

  • Repository checkouts
  • Build artifacts
  • Secrets
  • Any files a session creates or modifies

Sent to Anthropic for inference

  • Prompts and responses
  • Tool results — which can include code Claude reads
  • The stored session transcript (so a session resumes from any surface)

The distinction matters for a compliance review: self-hosting controls where your code and build outputs live and run, not whether the model sees the text of a conversation. The transcript is retained so work can be picked up from web, mobile, or desktop.

How it works

Runners, in two modes

You deploy a set of runners — long-lived processes that pick up sessions and start a Claude Code process for each one. A runner can serve more than one session, but each session runs in its own checkout, so work stays isolated between developers and accounts. Sessions from every supported surface route to the same environment, so you set it up once.

Mode 1

Fixed

You keep a set number of runners running and sessions are distributed across them — simple and predictable capacity.

Mode 2

On-demand

An orchestrator watches for queued sessions, starts a runner as work arrives, and stops it when work finishes — so capacity tracks demand.

This differs from Remote Control, which lets a developer continue a session running on their own machine from a phone or browser and ends when that machine stops. Self-hosted environments run on shared infrastructure your platform team operates and can be used by any user.

Before you turn it on

What availability and ownership look like

Self-hosted environments are available in public beta to organizations on Claude Team and Enterprise plans. They’re off by default and not available for organizations using zero-data-retention (ZDR). Plan for a platform, developer-experience, or developer-productivity team to own setup and ongoing operation — building and maintaining the runner image, updating runners, and running the orchestrator if you use on-demand mode.

Self-hosted environments let us integrate Claude Code into our existing workflows while maintaining our security and operational controls. — George Jacob, Senior Engineering Manager, Faire

What to do about it

Map your requirement first: if a compliance or network rule blocks vendor-hosted agent execution, pilot self-hosted environments and staff a platform owner for the runner image and orchestration. If not, default to the managed hosted offering — it’s the simpler, recommended route with nothing to maintain.
