When to Fold Subagents Into the Main Loop

Subagents give you verification, parallelism, and modular permissions — but Anthropic’s Applied AI team keeps finding that a single agent with skills beats an orchestrator-and-subagents design on quality, often at lower cost and latency. Here’s when to keep subagents, and how to fold the rest back into one loop.

The idea in five lines

  • One agent often wins — across enterprise deployments, a single agent with skills frequently beat both a one-giant-prompt design and an orchestrator-with-subagents design on quality, cost, and latency.
  • Multi-agent copies the org chart — each team ships its own subagent, so the architecture becomes Conway’s law in code, with sprawl, conflicting prompts, and latency no one owns.
  • Keep subagents for three cases — measurable context bloat in one loop, truly parallel work with disposable context, or a loop that keeps picking the wrong tools or fighting conflicting instructions.
  • Progressive disclosure replaces splitting — load skills and tools only when needed, so one agent can cover many tasks without a bloated system prompt or lossy handoffs between windows.
  • Migrate by evidence — build a small end-to-end eval, fold in one subagent at a time, and keep it only if the folded version scores worse.
So what for you

If a team is proposing a fleet of specialist agents with an orchestrator on top, ask for the eval first. Start with the simplest design that could work — one clear system prompt, a handful of thin tools, and skills — and only add a subagent when a measured problem forces it. Architecture you can’t measure is architecture you can’t safely simplify later.

The pattern

Simpler agents keep outperforming complex ones

Subagents — each with its own context window, tools, and instructions, orchestrated by a coordinator — are a legitimate design element, and Anthropic uses them in its own multi-agent research system. But when the Applied AI team compared enterprise deployments, a single agent with skills frequently outperformed both the “one prompt for everything” design and the subagent design, usually at lower cost and latency per task.

A common proposal stacks an intent classifier, a fixed reasoning pipeline, user-segment buckets, separate recommendation branches, and a multi-agent orchestrator on top. In practice, most of that structure is doing work the model no longer needs done for it — one clear system prompt, four or five thin data tools, and firm output guardrails cover most of the use case.

Enterprises often give each team or problem type its own subagent — so the architecture becomes a copy of the org chart. Conway’s law at work.

Where multi-agent breaks

Five failure modes of the org-chart architecture

Giving every capability its own agent and bolting on an orchestrator looks like the simplest path. It hides five recurring problems:

1 · Context

Lossy handoffs

You must decide what context passes between agents — and details get dropped in the back-and-forth.

2 · Sprawl

Subagent sprawl

Each team ships its own subagent, producing hundreds of overlapping agents with no standard and no clear owner.

3 · Prompt

The Frankenprompt

Every team adds a sentence to the system prompt, yielding conflicting rules and no consistent voice.

4 · Evals

Localized evals

Each team optimizes evals for its own subtask; no one owns the whole set, so leadership judges on watered-down scores.

5 · Latency

Nested loops add lag

Every subagent call is a nested model loop. One customer saw roughly 2× faster runtime from a single loop versus its multi-agent harness.

Keep them when

Three real reasons

Measurable degradation from context bloat; parallel tasks with disposable context; or one loop that keeps mis-selecting tools or hitting conflicting instructions.

The alternative

One loop, with progressive disclosure

Instead of an orchestrator handing work to specialists, let one agent see short descriptions of skills and tools and load them fully only when needed. Three reasons this wins:

Shared context

Better answers

For long-running work, one window that has seen every earlier step connects them better than summaries handed back by subagents — fewer windows, fewer lossy handoffs.

No bloat

Disclosure beats splitting

Progressive disclosure lets one agent cover many tasks without loading everything into a long prompt — removing the main reason teams split work.

Model capability

Models do more

Starting with Opus 4.5, models manage far more in one loop than teams expect; a simpler loop is also easier to migrate to the next model.

The target design

How to fold subagents into the main loop

The destination is one model and one context window running an open-ended tool loop, with limits — turn and cost budgets, write gates — set in the harness. Each turn the model emits a batch of tool calls; the harness runs them in parallel and returns raw results to the same model, which decides the next step. The planner is now also the executor, so it can revise its plan mid-turn as results arrive.

Figure 2 · Where the old orchestrator logic goes
1

Plan in context

The model writes its plan on turn one and rewrites it as results arrive — no separate planning step.

2

Procedure → skills

Ordering and domain know-how move into skills, disclosed when the task triggers them.

3

Limits → tools

Validation, approval gates, and lookups (memory, entity resolution) become tools the loop calls.

4

Verify & stop

The loop stops on an answer or a budget; an optional goal or verifier check runs after.

↻ Fold in one subagent at a time — turn its prompts into skills and its API calls into MCP tools, then compare evals with and without it.
Merge

Combine coupled specialists

Start with the most-used subagents and merge pairs that chain on each other’s output, touch the same data, or are often called together.

As a tool

Keep some as tools

When one of the three conditions holds, let the main agent call a retained subagent as a tool so it keeps the user conversation; reserve a full handoff for when the subagent must talk to the user directly.

Watch

Check what flipped

Look at which tasks changed, not just the score — one fold lowered latency but broke a passing process, and it only showed up in one of two runs. Run each task more than once.

How teams still contribute

Ownership moves from agents to skills and tools

MCP tools

Actions & live data

Right when the agent must act, read live data, or return a fixed shape. Group by user intent, not one tool per API — and use tool search with deferred loading.

Skills

How a team works

Right for the steps, rules, and judgment a specialist’s prompt used to hold. Per-team DRIs own their skills and ship them with evals; /skill-creator and /skill-doctor keep the library lean.

Knowledge bases

Reference, on demand

For material needed only sometimes — policies, metric definitions, specs. Put it behind a search or lookup tool, don’t have code paste it into every prompt.

One small central team should own the system prompt and end-to-end quality, vetting every new skill, tool, and eval before it ships. Per-user permission checks live inside each tool — it returns a plain refusal the model can read — so one loop can serve users with different access without a separate agent per permission level.

The discipline that makes it work

Measure, change one thing at a time, and keep what holds up. Build a small end-to-end eval, fold in one subagent, keep it as a subagent only if the folded version scores worse — then repeat. As models get more capable, more subagents can become skills and tools.
