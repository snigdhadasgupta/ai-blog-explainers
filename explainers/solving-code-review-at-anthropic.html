Reviewing code at the speed agents write it

Claude writes about 90% of Claude Code’s own code, so manual line-by-line review stopped scaling. The team’s answer: move most of the reading to machines, spend human attention only where risk is high, and make mistakes fast and cheap to undo.

The idea in five lines

  • The question changed — not “did a human read the code?” but “what could go wrong, and which check — automated or human — is the right one to catch it?”
  • Reading moved to machines — layered checks (Claude self-verification, AI review with verifier voting, security review, required CI, a merge queue) do most of the reading.
  • Approval is scaled by risk — a classifier sets a tier from the change itself: low merges with no human, medium needs one, high needs two. An agent’s approval never counts as a person’s.
  • Reversibility is the backstop — feature flags, internal-first rollout, staged release, and one-step rollback. “You land it, you own it.”
  • The guardrail is the metric — optimize for less human time per change while watching revert and incident rates. June–Sep, merged PRs more than doubled while reverts fell over 40%.
So what for you

You can borrow this even if agents aren’t writing your code yet: give the agent checks it can run (a short CLAUDE.md, linters, a fresh-context review), add an AI reviewer on one repo, scale human sign-off to risk, and make rollback cheap — then track human review time with reverts and incidents as the guardrail.

The reframe

Reading doesn’t scale — reversibility does

Human review time has two costs: the time spent reviewing, and the time spent fixing what bad code breaks. Cutting the first doesn’t help if the time just reappears as the second. So the team stopped treating “a human read every line” as the safeguard and instead built layers that each catch some problems and miss others — with fast rollback to handle whatever slips through.

“We didn’t remove review. We moved most of the reading to machines, optimized for human time and attention, and invested heavily in making it fast and easy to undo mistakes.”

The mechanism

The life of a change

Figure 1 · Layers each catch some problems; rollback handles the rest
1

Verify first

Claude runs tests, build, and linter; a second agent reviews the diff in fresh context before any PR opens.

2

AI review + CI

Required CI must be green; agents hunt bugs in parallel and verifiers vote — only findings enough agree on are posted, ranked by severity.

3

Security + approval

A separate security pass can block merge; a classifier then sets how many humans must sign off, by risk.

4

Merge & recover

A merge queue re-runs checks on latest main; flags, staged release, and one-step rollback catch the rest.

The hard part

Making review converge — and where humans stay

Convergence

Agent author + agent reviewer can loop

The reviewer was rarely finding new bugs — about 59% of its findings were old code already there. Fixes: cap at three rounds then step back, re-review only the new diff after the first passes, flag the class of bug not one line, and never repeat a posted finding.

Humans stay

Direction, risk, and accountability

People decide whether to build it at all, review risky code and pattern-setting architecture, and read the evidence. “A person is accountable for every change that ships, whoever typed it” — and an agent’s approval never counts as a person’s.

Honest limitation the team states: there are no circuit breakers yet that automatically tighten approval when reverts or incidents rise — engineers want them before more code moves to zero-human merges. The approval line “keeps moving.”

How to adopt this

Start on one repo: a short CLAUDE.md plus a REVIEW.md that says what failure looks like; add an AI reviewer and tune it for weeks before widening; require CI and resolved security threads; write risk tiers from the change, not the author; and make rollback one step. Measure human time per change — with reverts and incidents as the guardrail.
