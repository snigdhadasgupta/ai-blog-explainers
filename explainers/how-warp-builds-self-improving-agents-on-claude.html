How Warp Builds Self-Improving Agents

Feedback to an agent normally vanishes when the session ends. Warp’s fix is a two-skill loop: a base skill does the work, humans leave feedback where they already are, and an “improver” skill rewrites the base skill through a normal pull request — so the agent compounds instead of plateauing.

The idea in five lines

  • Feedback usually vanishes — when an agent session ends, the corrections humans made disappear, so the agent repeats the same mistakes forever.
  • Two skills, one loop — a base skill holds the domain knowledge; an improver skill observes accumulated feedback and proposes a small edit to the base.
  • Humans stay in control — the improver opens a normal PR; a person reviews, approves, and merges, and the next run inherits the change.
  • Skills are just files — because knowledge lives in plain files rather than the prompt, agents are good at editing them and updates flow through code review.
  • Any agent can compound — Warp now runs spec-writing, review, and triage agents that each carry their own self-improvement loop across its open-source repo.
So what for you

If you run an agent on a recurring task, add a lightweight way to capture feedback where people already work (a PR comment, a thumbs-up) and a scheduled job that turns that feedback into reviewable edits. That loop is the difference between an agent stuck at “80% right and annoying” and one that quietly gets better every week.

The problem

An 80% agent is a noisy agent

Warp — the AI-powered terminal and agentic development environment — hit this wall with its internal code-review agent. Engineers complained it left unhelpful comments and produced low-quality output. A first pass that gets 80% of a recurring task right still creates a noisy, annoying experience for the person on the other end.

The team tried the obvious stopgaps: manually rewriting the prompt after each observed failure, and improving context files like AGENTS.md. Both helped; neither scaled. The real issue was deeper — feedback to an agent typically disappears when the session ends, stripping the most valuable context out of the loop.

The framework is really simple: there’s the base domain-specific skill, and then there’s the improver skill that refines it. That simplicity is the beauty of the approach. — Zach Lloyd, Warp CEO

The mechanism

Two skills with a human in between

Figure 1 · The self-improvement loop
1

Base skill acts

The inner skill holds domain knowledge; the agent runs it to produce its output (e.g. a code review).

2

Human feedback

A person affirms or corrects the output where the work happens — ideally with the reason why.

3

Improver proposes

A scheduled observer skill reads accumulated feedback and drafts the smallest edit to the base skill.

4

PR merges in

The edit goes through normal code review; once merged, the next run inherits the improvement.

↻ The inner skill does the job; the outer skill runs on a schedule and refines it — a person approves every change.

Skills are file-based encodings of knowledge that keep instructions out of the raw prompt. Because they are plain files, agents are extremely good at updating them, and those updates are reviewable, approvable, and mergeable like any other code change. That final human step is what keeps a person in control of what actually changes.

The playbook

How to write self-improving skills

Principle

Write principles, not rules

Instruct the agent like a smart colleague. “Look for repeated code” generalizes better than exhaustive variable-naming rules — and explain the why so it can reason.

Signal

Make feedback effortless

Capture it where people already work — a PR or issue comment — with no extra submission step. Low friction is what keeps the signal flowing.

Structure

Keep skills small

Use progressive disclosure: a good skill references resource files and scripts rather than dumping everything into context at once.

Quality

Depth beats volume

A little detailed, domain-specific feedback from a senior engineer beats lots of binary thumbs up/down — because thumbs don’t say why. More quality signal still helps.

Reuse

Invest in the improver

The improver (observer) skill is largely reusable across use cases — the improver for a code-review agent isn’t that different from one for any other agent.

Guard

Assume feedback is wrong

Give the agent context to sanity-check input, filter whose feedback counts, and keep a human at the filtering or final-review stage.

The loop in action

Warp’s issue-triage agent

When someone files a GitHub issue, a GitHub Action fires an agent that analyzes complexity and feasibility, assigns labels, and suggests a direction. It runs off an inner skill holding domain knowledge about what each label means. On a sample issue it did a solid job but missed one label — ready to spec — and a maintainer left feedback directly on the issue, explaining both what he expected and why.

The outer improver runs in Oz, Warp’s orchestration platform, as a scheduled “update triage” agent. It authenticates to GitHub, runs a bundled Python script to pull issues carrying feedback, summarizes them into JSON, and reads that back into context. It then identifies the concrete signals and opens a PR making the smallest edit that captures them. A human reviews, approves, and merges — and the next triage run inherits the new knowledge.

Skills ≠ memory

Skills are procedural and stable — “how to do X,” changed deliberately. Memory is auto-written at inference time and never stops changing. Don’t conflate them.

One improver, or one per agent?

Meet in the middle: a templated base loop captures the overlap, with domain-specific weights layered on. A handful of agents can each own an improver; a hundred should share.

Is your domain verifiable?

If so, build the verification harness first, then let the agent tune against a reference corpus. If not, lean on deterministic evals against golden outputs and restrict human feedback to domain experts.

Is the whole system improving?

Track the global metrics humans already eyeball — time to merge, contributor count, cost — and feed them back into the improver agents. Go crawl-walk-run on deployment.

Build the loop in from the start

Any agent gets better over time if you capture human feedback signals, turn them into skill updates, and keep a person approving each change — expanding one-off helpers into systems that compound across your org. Pick one recurring agent task and add a base skill, a feedback channel, and a scheduled improver.
