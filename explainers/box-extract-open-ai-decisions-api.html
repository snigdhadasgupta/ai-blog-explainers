From upload to routed review

A certificate of insurance lands in Box. Box AI Extract pulls the fields from it and from the project’s requirements doc; OpenAI’s Decisions API picks one of three review routes; and a Box webhook opens the right review task — a working blueprint for intelligent document intake.

The idea in five lines

  • A document arrives, a decision follows — a certificate of insurance (COI) lands in a Box intake folder and an agentic workflow routes it for the right review automatically.
  • Two APIs, two jobs — Box AI Extract turns the COI and the requirements document into structured fields; OpenAI’s Decisions API picks the next step.
  • A typed choice, not a paragraph — the Decisions API returns one of three predefined routes with a confidence value, so the app never has to parse free text.
  • Box does the human part — a webhook creates a review task, assigns a reviewer, adds an insurance specialist when needed, and writes the extracted values and confidence as file metadata.
  • A pattern, not a product — the sample is demo code; production needs durable state, safe retries, and monitoring.
So what for you

This is a reusable shape for “intelligent intake” in any document-heavy process: pair structured extraction with a constrained decision step that returns a typed choice, fall back to specialist review when confidence is low or evidence is unclear, and keep the human review and audit trail in the system where the documents already live.

The shape of it

Intelligent intake, end to end

The scenario is mundane and universal: a vendor sends a certificate of insurance, and someone has to check it against the project’s requirements and route it to the right reviewer. Here, Box is where the document arrives and where people review it — the AI sits in between, reading the evidence and choosing a path, rather than replacing the reviewer.

The decision

Three routes, chosen by the evidence

Route A

request_endorsement

The COI is readable and coverage is present, but the separate additional-insured endorsement is missing. Open a task so the team can request the updated document; add the specialist as a collaborator.

Route B

specialist_review

A required date, limit, coverage detail, named party, or document is missing, unreadable, or contradictory. Assign a specialist and add them as a collaborator. This is also the fallback when confidence is low.

Route C

ready_for_human_review

The file appears to contain the requested coverage and a separate endorsement. Create a review task for a human to confirm.

The fields Box AI Extract pulls are the ones a reviewer would check first: project completion date, required liability limits, named insured, policy expiration, and additional-insured evidence.

Under the hood

Why two APIs, and what’s still on you

The handoff

Extraction feeds a typed decision

Box AI Extract turns each source document into a small set of requested fields; the Decisions API (default model gpt-6-luna) evaluates that context and returns a typed choice — “a typed choice instead of a paragraph the application must parse” — plus a confidence the app checks against its own threshold.

Before production

The demo isn’t the workflow

Box is explicit: this is not production software. Move event and processing state to durable storage, make retries safe, and add monitoring so failed or delayed submissions are visible. The sample PDFs are fictional.

Natural extensions the post suggests: search for existing project evidence and flag duplicates, handle multi-file submissions together, treat low extraction confidence on critical fields as its own review signal, and learn from completed reviews to refine prompts and thresholds.

Where this pattern pays off

Any high-volume intake with clear rules and messy inputs — insurance, onboarding packets, claims, compliance documents. Extract the fields, let a constrained decision step route the work, default to a specialist when unsure, and keep the review and the audit trail where the content already lives.
