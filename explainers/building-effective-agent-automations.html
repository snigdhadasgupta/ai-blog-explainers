Building Effective Agent Automations

A reference walkthrough for agents that run on a schedule, gather context in the background, and report only what matters — plus the quiet failure modes that break them. Built on Claude Managed Agents (beta).

The idea in five lines

  • Six parts to get right — Sources, Destination, Agent, Schedule, Memory, and Guardrails; the worked example is a daily brief that reads Slack and GitHub and posts to Slack.
  • Read from a bookmark, not a window — store the newest item seen per source; a fixed “last 24 hours” leaves gaps on late runs and repeats items on early ones.
  • A failed read is not a quiet day — if a source is down or a token expired, keep its bookmark, write the brief from the rest, and end with a line naming what couldn't be read.
  • Confirm before you record — a post counts as sent only when Slack returns ok and a message id; only then update the ledger and bookmarks, so a crash never double-posts.
  • Least privilege plus a budget — read-only tokens and an allowlisted network, and a spend cap set at three to five times a normal run that pauses — not fails — when hit.
So what for you

Before you ship a scheduled agent, write down its stop conditions and failure behavior first — most “flaky automation” is really an agent that silently lost a source or reposted yesterday's news, and the fixes here (bookmarks, confirm-before-record, re-read preferences) are cheap to build in up front.

The problem

The hard part isn't the model — it's trust

Simple agent automations run on a schedule, gather context in the background, and proactively report what matters. The trouble is they “can lose access to a source without anyone noticing or fail to follow our preferences.” Built on Claude Managed Agents, the reference runs on Anthropic's infrastructure after configuration, so nothing has to stay running on your machine.

An item earns a line when the reader would act on it today, or it changes a decision they are about to make. When unsure, leave it out.

Why it matters

One stale update costs more than ten missing items

An unattended agent that posts a confident but wrong “still waiting on you” burns more trust than one that quietly misses something. The six components below are the scaffolding that makes a scheduled agent reliable enough to run without a human watching — and the pattern generalizes well beyond a Slack brief.

The anatomy

Six components of a reliable automation

Sources

Read with least privilege

Slack and GitHub by default; credentials live in vaults, with MCP calls routed through a proxy and tokens swapped in only for allowlisted hosts as the request leaves the sandbox.

Destination

One dated post, confirmed

One Slack channel, one post per run. A post counts as sent only when Slack returns ok and a ts; if unclear, the run is marked “maybe posted” and nothing else changes.

Agent

Versioned config, verified

Model, prompt, and tools are pinned; the agent re-checks each item against its live source just before posting, never hedges a status, and copies links from the source's own field.

Schedule

Fresh session each run

A cron deployment names the agent, environment, budget, and first message; each trigger starts a clean session with no memory of the last.

Memory

Two stores, two owners

Read-only preferences (channels, repos, length cap) and read-write state (bookmarks, ledger, run records). Re-read preferences every run; if unreadable, stop rather than run on defaults.

Guardrails

Read-only, allowlisted, capped

Read-only tokens, network limited to allowlisted hosts, and a spend cap that pauses with budget_reached instead of failing.

The rules that prevent silent failure

Bookmarks, confirmation, and honest status

Do

Bookmark, don't window

Store the newest item seen per source and read from there. Report a down source or expired token as unreadable in the post — never let a failed read look like a quiet day. Count a post sent only when Slack confirms it, then update bookmarks and the ledger.

Start

From the reference, not from scratch

Update Claude Code, run the claude-api managed-agents-onboard skill, and it writes an agents/ folder and creates resources with ant apply. Code lives at anthropics/claude-quickstarts under managed-agents/daily-brief — treat it as a starting point.

Try the reference implementation
