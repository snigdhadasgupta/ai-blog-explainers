When AI Infrastructure Becomes the Target

Gateways, retrieval platforms, and orchestration services now sit between users, apps, data, and models — concentrating credentials, data access, and execution privileges. Microsoft Threat Intelligence found attackers treating that concentration as a control plane, hitting a LiteLLM gateway, a RAGFlow deployment, and a Kestra workflow with strikingly similar goals.

The idea in five lines

  • AI infra is now a target — Gateways, RAG platforms, and orchestrators concentrate credentials, data, and execution — making them some of the most powerful and attractive parts of the stack.
  • Three compromises, one pattern — A LiteLLM gateway, a RAGFlow deployment, and a Kestra workflow were hit via different paths but the same objectives: steal credentials, persist, monetize compute.
  • Gateways are Tier-0 secrets stores — A compromised LiteLLM proxy exposed provider keys, master keys, virtual-key records, and database connection strings from the process environment.
  • Theft and mining converge — Attackers deployed XMRig miners, harvested secrets, and installed persistence — with some payloads showing signs of AI-assisted development.
  • Defenses are conventional — Patch and authenticate gateways, scope credentials, apply least privilege, constrain egress, and monitor application-origin shells.
So what for you

If your teams are standing up self-hosted AI infrastructure, inventory those management surfaces now. Treat an AI gateway like a Tier-0 secrets store — never exposed to the internet, authenticated on every surface, with per-team keys and deny-by-default egress — because the same concentration of trust that makes it useful makes it a target.

Why it matters

AI workloads have become control points

AI is creating a new layer of enterprise infrastructure. These systems concentrate credentials, data access, model connectivity, and execution privileges — and that concentration of trust creates opportunity for attackers. Across three investigations, the individual techniques varied but the broader pattern held: attackers treated AI infrastructure as a control plane where credential theft, host compromise, and downstream data access converge.

These platforms are becoming high-value targets that deserve the same security scrutiny as other critical enterprise infrastructure.

Three compromises

Different entry points, same objectives

Gateway

LiteLLM

Python droppers, runtime secret harvesting, PostgreSQL collection, miner deployment, and persistence from the gateway context. Likely entry: an exposed surface (CVE-2026-42271 chained with CVE-2026-48710).

Retrieval

RAGFlow

SSRF-style reconnaissance, then code execution and a Python hook planted in the credential-configuration flow to intercept newly configured LLM provider keys.

Orchestration

Kestra

Workflow-origin shell execution, Docker and container discovery, XMRig deployment, and follow-on data collection for secret discovery and compute monetization.

Inside one attack

The LiteLLM gateway chain

LiteLLM sits as a proxy between applications and model providers, so it holds or retrieves provider keys, master keys, virtual-key records, connection strings, and routing config. Command execution in that runtime put the attacker close to credential material. The chain: harvest credentials from the gateway process environment; deliver and masquerade a payload; prepare cryptomining and remove competing miners; reach the LiteLLM database through Azure PostgreSQL; then establish persistence, command-and-control, and defense evasion.

Notably, several payloads showed hallmarks of AI-assisted development — organized imports, explicit timeout handling, dependency fallbacks, and explanatory comments — a more structured style than typical one-off shell payloads.

The mitigations

Conventional controls on a new surface

Figure 1 · Microsoft's mitigation guidance
1

Treat gateways as Tier-0

Patch proxies, require auth on API and UI, restrict management ports, never expose to the internet.

2

Scope credentials

Per-team virtual keys with spend limits, upstream keys in a managed secret store, rotate on exposure.

3

Least privilege

Dedicated service accounts, minimal DB permissions, private endpoints, and cloud monitoring.

4

Constrain egress

Deny-by-default outbound, allowlist model-provider endpoints, block raw-IP and non-standard ports.

↻ Correlate application-origin shells with secret access, Docker socket use, outbound callbacks, and resource-hijacking — not product-specific indicators alone.

What to do now

Inventory exposed AI management surfaces, restrict administrative access, and monitor for gateway-originated execution and secret access. The controls are familiar — patching, authentication, least privilege, egress filtering — but they now have to cover gateways, retrieval platforms, and orchestrators that most inventories don't yet track.
