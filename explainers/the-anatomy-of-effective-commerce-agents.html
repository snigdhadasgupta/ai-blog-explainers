The Anatomy of Effective Commerce Agents

Retailers, marketplaces, and travel platforms run shopping and merchant agents on Claude. The pattern that works is deceptively simple — one model in an agent loop with skills, not a maze of subagents — and the real engineering is in latency, cost, and harness-enforced safety.

The idea in five lines

  • One model, one loop — a commerce agent is a single model in a standard agent loop with skills and tools, with no intent router in front and no subagent swarm behind.
  • Skills beat subagents — handoffs are state-lossy and cost extra tokens and seconds, while skills give per-domain modularity inside the agent that already holds the whole session.
  • Prompt or skill by frequency — anything roughly a third of traffic touches (plus all safety and legal rules) lives in the system prompt; the long tail loads as skills.
  • Design for the cache — the best deployments run 90–99% prompt-cache hit rates by ordering context global → session → turn so the warm prefix pays for itself.
  • Safety lives in the harness — the model only stages an action, a person or policy applies it, and every write or render accepts only server-issued IDs.
So what for you

If you are scoping an agent build, resist splitting it into a subagent per domain. Start with one agent, put high-frequency behavior in the system prompt, and design your context ordering for prompt caching from day one — those three choices set your quality, latency, and cost ceiling before you write a feature.

The shape that works

A single model in a loop, not an org chart of agents

A commerce agent simplifies buying and selling across an online catalog — a retail cart, a travel itinerary, a plan change, or a merchant asking what to discount. The core architecture is one model in a standard agent loop: it reasons about a goal, explores context through tools, learns procedures through skills, asks clarifying questions, and observes results until the task is done. There is no intent router segmenting the conversation and no set of domain-specific agents behind it.

The tempting alternative — one subagent per domain — underperforms, because a commerce conversation is one tightly coupled session across many intents that share cart, preferences, and history. Every handoff is state-lossy, can cost several times the tokens, and adds seconds of latency, and the domains rarely separate cleanly (a returns flow needs order history, the current cart, and the catalog at once).

A single agent with skills consistently outperformed both the one-prompt-for-everything design and the subagent design on quality — often at lower cost and latency per task.

Subagents still earn their place as a tool for a narrow, self-contained job that deserves its own context window — a deep-research subagent that reads, writes code, and returns a compact answer. And a domain with its own purpose-built agent (a pharmacy or financial-services flow with its own compliance surface) warrants a true hand-off, where that agent owns the conversation rather than being bounced in and out mid-turn.

The agent loop

Four moves, repeated until the goal is met

1

Reason about the goal

Plan the next step from the full session context the agent already holds.

2

Act through tools

Call the catalog, cart, inventory, or pricing systems you already run — in parallel where independent.

3

Load skills for the long tail

Per-domain instructions load into the same agent, no handoff and no lost state.

4

Observe & continue

Read the results, ask a clarifying question if needed, and loop until done.

Placement

Prompt or skill? Decide by frequency

Loading a skill costs a model turn, so anything the agent needs on most turns goes in the system prompt. A good starting rule: anything relevant to a third or more of traffic — anticipated or observed in production — goes in the prompt, and the rest goes in skills. Critical instructions (safety and legal rules, brand constraints, key user facts like allergies) always go in the prompt. If a skill is predictable from a signal you already have, such as the page the user arrived from, inject it from the harness before the first model call.

Shopping agent

In the prompt

Grounding, cart and checkout semantics, presentation rules, and product search — nearly every session touches these.

Skills (the long tail): search-discovery · purchase-research · planning-goals · customer-care · memory-personalization.

Merchant agent

One skill per domain

The merchant agent splits the same way, with a skill for each operational domain the store runs.

Skills: performance-insights · catalog-listings · inventory-operations · pricing-promotions · marketing-campaigns.

Latency & cost

Make it fast and affordable without spending intelligence

Quality of outcome moves retention, engagement, and cart size more than marginal latency gains — so attack latency on two fronts and let caching carry the cost. Task-completion latency is the sum over turns of time-to-last-token plus tool processing, which gives three levers: fewer turns, faster tools, faster tokens. Minimize the sum, not any one lever.

Production hardening

Memory, safety, and evals keep it in production

Memory

Store it in your systems, write it async

Keep facts as small typed records in the database you already run, keyed by person for shared merchant logins. An async extractor reads only user and assistant text at turn end — adding no latency and scoring 13% higher fact recall than a save-tool. Read in three layers: always-in-context, pre-fetched per turn, and behind a lookup tool.

Safety

The model stages; a person or policy applies

No model tool call moves money or changes the business. Checkout renders a cart with a button and the backend has no charge method; every merchant write produces a staged change that apply_change accepts only after real approval. Writes and renders accept only server-issued IDs, re-checked against current limits at apply time.

Evals

Ship a non-deterministic system on evidence

Choose the model and its configuration by sweeping an eval suite rather than guessing, and let production traffic — turns per task, cache rates, recall — tell you what to move into the prompt and what to leave in skills.
