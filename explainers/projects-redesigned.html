Projects Redesigned: From Folder to Conversation

Claude Code projects stop being a place to park files and start coordinating the work. You describe a goal, and a coordinator chat breaks it into pieces, runs them in parallel across worker threads, reviews the outputs, and assembles the result — while you watch from your phone.

The idea in five lines

  • A project is now a conversation — not a folder of files. You state a goal and Claude plans, delegates, and assembles the work rather than waiting for one prompt at a time.
  • A coordinator routes to threads — a top-level chat splits the goal into worker threads, each a Claude Code cloud session running on its own branch and repo copy.
  • Threads run in parallel and can split further with subagents, loops, and workflows — e.g. a separate thread per repo to retire a deprecated API endpoint across API, web, and mobile.
  • Shared memory and a library keep decisions, schedule changes, added files, and Claude-generated artifacts in one place that every thread reads from and writes to.
  • Beta in Claude Code for select Pro and Max cloud-session users; you tune check-in frequency, update detail, and the model and effort for coordinator and workers.
So what for you

If your team lives in Claude Code, start framing work as a goal, not a task list — "reduce checkout latency," not "profile endpoint X." The new project model is built to decompose and parallelize that goal for you, but watch project-level usage: several threads burn through limits faster than a single session.

What changed

From a place for files to a place that does the work

The old project was a container: you dropped in files and context, then opened a chat against them. The redesign flips that. A project now holds a coordinator conversation that treats your goal as something to break down, run, and review — so work continues after you step away, and you can monitor progress from your phone.

You describe the outcome you want; Claude breaks it into pieces, runs them in parallel, reviews the outputs, and assembles the results.

Two examples from the announcement make it concrete: profiling slow endpoints and opening pull requests in parallel to cut checkout latency, and retiring a deprecated API endpoint across API, web, and mobile repositories — with a dedicated thread for each repo so the changes move together but stay isolated.

Memory

A shared project brain

Threads add to and draw from a common memory that tracks details like schedule changes and decisions, so parallel work doesn't drift out of sync.

Library

Files + artifacts in one place

The project keeps a library of files you add and artifacts Claude generates, available to every thread rather than scattered across sessions.

Control & limits

Tuning cost, cadence, and where threads run

CadenceCheck-ins and update detail are yours to set
Adjust how often Claude reports back and how detailed those updates are — from a light touch to step-by-step.
UsageWatch project-level consumption
Multiple threads reach usage limits faster. A project-level usage view, plus per-role model and effort choices for the coordinator and workers, let you trade cost for speed.
LocationCloud today, local planned
Threads currently run in the cloud. Running locally — alongside local tools and behind your network — is on the roadmap.
AccessBeta, then broader
Open to select Pro and Max subscribers who use Claude Code cloud sessions and have no existing web or desktop projects; a waitlist is live. Broader Claude Code access comes next, then Team and Enterprise. Existing projects keep working as they do today.

Where to start

Pick one multi-repo or multi-step goal your team keeps doing by hand — a migration, a latency pass, a cross-surface change — and run it as a single project goal. Set a conservative check-in cadence and a sensible model/effort mix first, then watch project usage before you scale the pattern up.
