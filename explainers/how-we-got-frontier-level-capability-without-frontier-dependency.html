Frontier Capability, Without a Frontier Dependency

Box’s security team built an agentic pen-testing engine that finds deep logic flaws its scanners were never designed to catch — running on a laptop, with a dozen models from six vendors, and an open-weight model producing most of the validated findings.

The idea in five lines

  • The threat changed — finding a deep logic flaw used to cost weeks of expert time; AI collapsed that cost for defenders and attackers at the same moment.
  • Box chose constraint over horsepower — not one all-powerful agent roaming the platform, but a grounded ensemble scoped by architecture and checked by deterministic code.
  • Build the boundary first — every action runs through one policy-gated, rate-limited core writing only to disposable canary objects in non-production; the scope lives in code, not a prompt.
  • A non-AI oracle is the judge — a finding only ships when deterministic code independently reproduces the exploit end to end and re-runs it; a model’s confident guess never reaches the report.
  • The best model wasn’t the best here — an open-weight model out-produced the top frontier reasoner ~7× on validated leads; benchmark rank barely predicted results.
So what for you

If your teams are pointing autonomous agents at real systems, the model is rarely the hard part — grounding and proof are. Before you buy the most capable model, decide what enforces the blast radius and what independently verifies a claim, because those are what make an agent’s output something you can act on.

Why it matters

Scanners find what they were told to look for

Traditional scanners are excellent at matching known patterns, signatures, and bad payloads. But the most dangerous flaws in a multi-tenant platform are different: valid requests, correct syntax, an authorization decision made on the wrong basis. There’s no signature to match. Finding them means understanding what the system is supposed to permit, forming a theory about where it permits more, and testing it — work whose expense used to deter attackers. It doesn’t anymore.

None of what we built came from trying to spend less. It came from realizing the model was never the bottleneck. Grounding and proof were — and those get built, not bought.

The architecture choice

Two credible designs; one you can rely on

Rejected

The maximalist agent

One very capable agent, broad latitude, unlimited compute, left to roam. Minimal engineering and it improves as models do — but it’s opaque (findings arrive as assertions), unconstrained (a big compute bill and an undefined blast radius), and spends its budget rediscovering what your own architecture docs already state.

Chosen

The constrained ensemble

Grounded in real source. Discovery spread across a dozen-plus models from six vendors. Every claim terminates at a deterministic oracle that reproduces or discards it. Cheap enough to run on a cadence, small enough to audit line by line, scoped by architecture rather than by prompt.

The bet: a smarter model doesn’t make an unproven finding actionable, and no amount of reasoning substitutes for reading the authorization path. So the effort went into scaffolding, not procuring the single best brain.

The pipeline

Six stages, one enforced boundary

The most important piece isn’t exciting: every path to a target runs through a single policy-gated execution core — rate-limited, writing only to disposable canary objects it created, restricted to non-production. Production is strictly read-only. It’s the only code path that exists. Inside that boundary, the pipeline runs six stages; the two that touch recon and verification are deliberately model-free.

Anti-pattern

Don’t scale one strong model

Blind spots correlate inside a model family, so parallel agents with identical instincts walk past the same flaw at high confidence. Coverage looks like a compute problem but is really a diversity problem.

Where FPs die

The oracle can throw AI work away

A claim the oracle can’t reproduce is demoted to a labeled lead, duplicates collapse into one finding, and a “leak” only counts if a benign request doesn’t produce the same error. Demoted, never silently dropped.

The operational catch

A refusal looks exactly like a clean result

Several frontier providers filter offensive-security work — including authorized, owner-initiated testing of your own systems. That’s a reasonable product decision. The problem is how refusals surface: nothing crashes, the run completes, and the only trace is an absence. A result that produced nothing looks identical to a result that found nothing.

Frontier — for depth
Stronger when an agent holds one theory and must chain three conditions to prove it, and at reading unfamiliar code and reasoning about an unfamiliar weakness.
Open-weight — for breadth
Produced the bulk of validated leads at a fraction of the cost, ran under terms that permit authorized testing, and held the single highest-yield exploit slot.
The backstop rule
Every declined unit is detected, logged, and re-dispatched to an open-weight model — and the refusal rate is surfaced in run health, so coverage is a number you can claim.

If you’re building something like this

Start with one weakness class your team understands and wire one oracle for it. Prove a single bug end to end — hypothesis, exploit, independent reproduction, a ticket an engineer closes. Then add lenses and models to a machine that already knows how to tell proof from suspicion. Build the boundary and the oracle first, and the models become interchangeable.
