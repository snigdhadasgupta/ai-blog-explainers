The New Rules of Context Engineering for Claude 5 Models

Anthropic deleted more than 80% of Claude Code’s system prompt for its newest models — with no measurable loss on coding evals. The rules that got you here are now myths. Here’s what replaced them.

The idea in five lines

  • A prompt is one message; context is everything assembled around it — system prompt, Skills, CLAUDE.md, memory. Engineering that context drives your results.
  • Newer models have better judgement, so guardrails that protected older models now over-constrain them. Anthropic removed 80%+ of Claude Code’s system prompt with no measurable loss.
  • Seven old best practices flipped: give rules → let Claude judge; give examples → design interfaces; front-load everything → progressive disclosure.
  • Spend your tokens where they matter: product context in the system prompt, gotchas in CLAUDE.md, opinions and know-how in Skills.
  • Run /doctor in Claude Code to rightsize your own Skills and CLAUDE.md files automatically.
So what for you

Audit your own agent's system prompt for rules, examples, and repetition you no longer need — with capable models, trimming context often improves results rather than hurting them.

Why this matters

Prompting is a sliver. Context is the rest.

When you send a message to Claude, the prompt is only a small part of what it actually receives. The rest is assembled from your system prompt, Skills, CLAUDE.md files, memory, and other sources. Anthropic calls this context engineering, and unlike a one-off prompt, context is reused across many requests — so it can’t be as specific, and small mistakes compound.

The cause is capability. Older models needed strong, sometimes-wrong guidance to avoid worst-case behavior — and reading their own transcripts, the team found conflicting instructions in a single request (“leave documentation as appropriate” colliding with “DO NOT add comments”). Newer models can read surrounding context and use judgement, so many of those constraints can simply be deleted.

We were over-constraining Claude Code — and once we stopped, the model used context and judgement to get to the right answer on its own.

The flip

Then & now: seven rules that reversed

Each of these was once the right call. With more capable models, the opposite is now true.

Then

Give Claude rules

Hard-code strong guidance (“default to no comments”) to avoid worst-case output.

→
Now

Let Claude use judgement

“Write code that reads like the surrounding code” — match its comment density, naming, and idiom.

Then

Give Claude examples

The number-one rule for tool use was to show worked examples.

→
Now

Design interfaces

Examples constrain exploration. Make parameters expressive instead — a status enum of pending / in_progress / completed hints usage on its own.

Then

Put it all upfront

Load every detail (code review, verification) into the system prompt in case it’s needed.

→
Now

Use progressive disclosure

Move rarely-needed detail into Skills and deferred-loading tools that Claude fetches only when the task calls for them.

Then

Repeat yourself

Duplicate tool instructions in both the system prompt and the tool description.

→
Now

Simple tool descriptions

Put usage instructions in the tool description only. Delete the repeats.

Then

Memory in CLAUDE.md

Prompt users to save facts with the # hotkey.

→
Now

Auto-memory

Claude now saves memories relevant to the work and to you, automatically.

Then

Simple specs

Store plans and specs as plain markdown files for Claude to reference.

→
Now

Rich references

A spec can be an HTML artifact, a test suite, a function to port, or a rubric a verifier agent grades against.

Apply it

Where to spend your tokens

Pulling it together, here’s how to think about each layer of context you control.

01

System prompt

Tied to product context — what Claude is and what it’s doing. In Claude Code you’ll never touch it; building your own agent harness, this is where to invest the most effort.

02

CLAUDE.md

Keep it light. Briefly say what the repo is for, then spend the tokens on gotchas — e.g. “types live in one monolithic file.” Skip the obvious things Claude can see from the file system.

03

Skills

Lightweight guides Claude loads when needed. Encode opinions, knowledge, and practices specific to you or your team. For long skills, split into many files and disclose progressively.

References beat descriptions. You can @-mention files — specs, mockups, whole codebases — as references. Prefer files that are in code: a HTML mockup generally produces better results than a screenshot or a prose description of the same design, because it’s high-fidelity in a language Claude knows well.

The throughline: across your system prompt, Skills, and CLAUDE.md, you probably need to simplify — just like Anthropic did. Trust the model’s judgement, disclose progressively, and reserve explicit rules for the few genuinely high-stakes cases.
