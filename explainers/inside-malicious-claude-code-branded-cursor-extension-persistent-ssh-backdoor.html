A Trojanized AI Coding Extension

For a few hours, a tampered copy of the Claude Code extension sat in the Cursor marketplace. On load, it planted an SSH key, opened a reverse tunnel back to an attacker, and set up persistence across macOS, Linux, and Windows — a sharp lesson in treating your editor’s extension marketplace as a supply chain.

The idea in five lines

  • A trojanized Claude Code extension — tampered copies (v2.1.313 and 2.1.312) appeared in the Cursor marketplace for a few hours on Oct 29 before Cursor pulled them.
  • Limited blast radius — the bad packages never reached the Visual Studio Marketplace or npm, and Microsoft says Anthropic’s own systems were not compromised.
  • It ran on load — injected JavaScript fired the moment the extension module loaded, using only built-in system tools and embedded keys, and hid its own errors so the editor kept working.
  • A persistent SSH backdoor — it planted an SSH key, opened a reverse tunnel to the attacker, and set startup persistence on macOS, Linux, and Windows.
  • Careful, not conclusive — Microsoft maps the behavior to MITRE techniques but makes no attribution and confirms no credential theft; host hardening often blocked the SSH step.
So what for you

If your developers install editor extensions, treat a third-party extension marketplace as an untrusted supply chain: allowlist approved publishers, add a cooldown before newly published versions can be installed, and check developer machines’ authorized_keys for unexpected entries. A trusted brand name on an extension is not, by itself, a trust signal.

What happened

A trusted name, a tampered package

On October 29, 2026, Cursor reported that tampered copies of the Claude Code extension — identified as anthropic.claude-code, versions 2.1.313 and 2.1.312 — had been served in its marketplace for a few hours, roughly 2:27 AM to 1:35 PM PDT. Microsoft confirmed the malicious packages were never published to the Visual Studio Marketplace or to npm, and Anthropic told Microsoft its systems were not compromised and that it did not build the package.

The malicious code ran from an extension’s module load — inside the trusted tool — using only built-in system tools and embedded components, while the extension continued functioning normally.

That last point is what makes this worth studying: there was no second-stage download to catch on the network, no crash to notice. The loader lived off the land, suppressed its command output, and silently swallowed errors so nothing looked wrong.

The attack chain

Five steps, all from a single module load

Figure 1 · What the loader did, in order (per Microsoft’s analysis)
1

Recon

Collects hostname, user, OS, home and working dirs, git email; scans env-var names for KEY, TOKEN, SECRET, AWS, GCP.

2

SSH key

Appends an embedded Ed25519 public key to authorized_keys (tagged svc-telemetry) and tries to enable local SSH.

3

Reverse tunnel

Opens an outbound SSH connection asking the server to forward back to the workstation’s port 22.

4

Persistence

Writes a LaunchAgent, an @reboot cron entry, or a scheduled task to relaunch on restart.

5

Report

A delayed callback sends host details and matching env-var names — not values — to attacker infrastructure.

↻ No second-stage download — it lived off the land with embedded keys and system tools, and swallowed errors to stay hidden.

Microsoft is careful to note the sequence “does not prove that every step succeeded on every host.” Cursor reported that errors and administrator-permission requirements blocked the SSH step on most macOS and Windows machines — though the key-planting, persistence, and host reporting could still have happened.

Inside the backdoor

Two SSH identities and a retry loop

The backdoor used two separate SSH identities: one to let the attacker in, and one to dial out. Neither was downloaded — both were embedded in the tampered package.

Victim key

Inbound access

An embedded Ed25519 public key is appended to authorized_keys so whoever holds the private key can log in as the user — gated only by the host’s SSH configuration. The loader first checks for the comment svc-telemetry and skips if already present.

Tunnel key

Outbound dial-home

A separate private key, written to a hidden file matching .stk_[0-9a-f]{10}, authenticates a reverse tunnel launched with ssh -N -R '*:0:localhost:22' — asking the server to forward connections back to the victim’s port 22.

Retry loop

Staying connected

On Unix it prefers autossh and falls back to ssh; on Windows a hidden PowerShell loop. Each waits 60 seconds after exit and retries, with host-key checking disabled and prompts suppressed.

Persistence, disguised as monitoring

Names like “SysMon” and “com.apple.sysmond” were chosen to look like legitimate monitoring components. Microsoft stresses that an artifact’s presence alone does not prove the mechanism ran.

macOS
User LaunchAgent with RunAtLoad + KeepAlive at ~/Library/LaunchAgents/com.apple.sysmond.plist, plus .smt / .smtk scripts in ~/.config.
Linux
A user-crontab @reboot entry that rebuilds the .smtk identity and restarts its own SSH retry loop.
Windows
An attempted “SysMon” scheduled task requesting SYSTEM execution (%USERPROFILE%\.config\smt.cmd), with a Startup-folder sysmon.cmd batch file as fallback.
Indicators & detection

What to hunt for, and first moves

Indicators

Signs of this backdoor

  • C2 IP 134.209.82[.]225 and beacon hxxp://134[.]209[.]82[.]225:8099/beacon
  • authorized_keys entry commented svc-telemetry
  • Temp files matching .stk_[0-9a-f]{10}
  • Startup items named SysMon or com.apple.sysmond
First moves

If you suspect exposure

  • Hunt for installs or auto-updates of anthropic.claude-code 2.1.313 / 2.1.312 from the Cursor marketplace
  • Check authorized_keys for svc-telemetry; verify the key fingerprint before removing the exact entry
  • Preserve evidence, then remove the extension and its persistence — inspect each startup object’s action, since names alone are not enough
  • Rotate any in-scope credentials from a clean device

Microsoft notes these strings and paths “should not be treated as conclusive evidence of compromise on their own,” and that removing the extension does not remove artifacts written outside its install directory — Cursor’s server-side takedown does not clean endpoints.

What to do now

Removing the extension isn’t enough. Hunt for the affected versions, check authorized_keys and startup items on developer machines, rotate any credentials that were in scope, and harden your editor supply chain with publisher allowlists and an install cooldown for newly published extension versions.
